# Nirili Villa — self-hosting handover

Source snapshot: 7178c6c3232bfd529e3df8d5f6a93fa8a14bf430 (13 September 2026).
Includes full application source, pinned dependencies, SQL migrations and build configuration. This is an export copy; the existing hosted system is unchanged.

## Hosting target
Cloudflare Workers with a D1 database binding named DB. This is not a static HTML/PHP website and cannot simply be uploaded to cPanel. A different server/database platform requires porting the Cloudflare bindings.
Install Node.js 22.13+ and pnpm (package.json records the original package manager version). Run commands from this extracted folder. The included build passed before export; deployment to your account has not been tested.

## Install and configure
1. Run `pnpm install --frozen-lockfile`.
2. Run `pnpm exec wrangler login` to log into YOUR Cloudflare account.
3. Run `pnpm exec wrangler d1 create nirili-villa-db`. Copy its database UUID.
4. Run `node self-host-setup.mjs YOUR_DATABASE_UUID`. This writes your deployment configuration and generates a fresh admin login plus encryption key in private local files. It refuses to overwrite them. Keep them private and backed up.
5. Run `pnpm exec wrangler d1 migrations apply DB --remote --config wrangler.selfhost.json` to create tables. Read and approve the target database shown by Wrangler.
6. Run `pnpm exec wrangler secret bulk self-host-secrets.json --config wrangler.selfhost.json` to configure the required NIRILI_BOOTSTRAP and NIRILI_CREDENTIAL_KEY secrets. If Wrangler asks to create the Worker, allow it.
7. Run `pnpm build`, then `node self-host-config.mjs YOUR_DATABASE_UUID`, then `pnpm exec wrangler deploy --config wrangler.selfhost.json`.
8. Open the HTTPS address Wrangler returns. Select Admin and use the login in ADMIN-LOGIN.txt. Create staff accounts in Users, then review room rates, menus and bookings before use.

The app contains demo/default hotel records in source. Review those before live operation; this archive does not claim to be an empty production database. Staff seed password hashes were deliberately removed from two exported SQL migrations; create your own cashier/waiter accounts.

## Rebuild after editing
Run `pnpm build`, then `node self-host-config.mjs YOUR_DATABASE_UUID`, then deploy with the command above. The config script refreshes the deployment config from the generated Worker config without changing your secrets. Keep the DB binding named DB. Do not use the original Sites project identifier to deploy to your own account.

## Current business data and migration
This download DOES NOT include the live D1 database, existing guests/bookings/bills, active sessions, or hosting secrets. The SQL files define structure, not a backup. No production data was removed or changed.
To move existing records, obtain an authorized database SQL export from the current hosting environment, then import it into your own D1 database. Do not run fresh-install migrations over a full imported schema without checking migration history. Accounts and operation_records must move together: room bills, bookings, orders and credential records are linked. Existing password hashes can move; encrypted password display/share also needs the original NIRILI_CREDENTIAL_KEY through a secure transfer. If unavailable, reset those passwords and reissue room logins. Do not migrate active account_sessions; users should sign in again. Set NIRILI_BOOTSTRAP to [] when using an imported database that already has admin accounts, to avoid seeding an extra admin.

After hosting in your own account, a backup command is:
`pnpm exec wrangler d1 export DB --remote --config wrangler.selfhost.json --output nirili-backup.sql`
Store backups and encryption keys securely, separately from this source bundle. Test a restore before relying on backups.
